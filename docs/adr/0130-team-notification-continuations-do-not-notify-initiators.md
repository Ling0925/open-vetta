# ADR-0130：通知派生的 Team 续跑不再反向通知发起者

## 状态

已接受

## 背景

ADR-0115 要求成员收到任务完成通知后，继续在 Team attempt 中生成可发布的回答；ADR-0125 要求通知及其接收凭据持久化。发起成员的最近工作项已结束时，协调器会为这次通知创建新的后续工作项，并沿用最近工作项的 `createdByParticipantId`。

当两个成员先委派任务、再相互提问时，后续工作项的发起者可能恰好是另一个成员。后续工作项完成后又被当成新的委派任务通知对方；对方再创建后续工作项，如此往复。每轮的工作项 ID 和 revision 都不同，所以通知去重与单项自动恢复预算无法阻断整条链；会话直到用户手动停止才结束。

## 决策

1. 新建的通知派生后续工作项持久化可选的 `notificationContinuation: true`。它仍是正常的 Team attempt，保留模型续跑、结果发布、失败分类和原有恢复能力，但完成或受阻后不再向 `createdByParticipantId` 发起新的任务通知。
2. 原工作项处于 `waiting` / `attention-required` 时，通知仍恢复原工作项，不加此标记；实际委派任务和成员提问的完成、失败及阻塞仍正常通知发起者。没有既有工作项时的通知续跑也标记为内部后续工作项。
3. 历史记录缺少该字段时，只有同时具有持久化通知接收凭据、系统生成的 `:continuation:<n>` 工作项 ID、且能找到同一执行成员与发起者的原请求工作项，才按旧版内部后续工作项阻断反向通知。不根据英文 objective 或单独的 `notificationIds` 推断来源，不批量改写会话历史。
4. 停止团队、用户新消息解除停止、通知接收去重与原工作项恢复预算继续采用 ADR-0125 的语义；本修复仅切断内部后续工作项作为新通知生产者的路径。

## 备选方案

- 只按通知 ID 或工作项 revision 去重：每次反向通知都来自新的工作项，无法识别跨工作项的因果回路。
- 禁止所有携带 `notificationIds` 的工作项发通知：被中断的真实工作项恢复后也可能携带接收凭据，会漏掉其应有的最终结果或阻塞状态通知。
- 为通知链设置固定轮数或时间上限：只能限制损失，不能区分正常多轮协作与内部回传。

## 后果与边界

原任务的结果仍会唤醒发起者，发起者的可见续跑回答仍发布到团队时间线；仅用于整合通知的工作项不会再次唤醒对方。旧会话无需迁移即可读取；升级前已经写下的待交付通知可能先触发一次续跑，但新续跑不会继续生成回传链。新字段可选，旧数据与公共工作项读取者保持兼容。

通知接收者目前仍以其最近工作项决定回答归属；当近期有多个独立请求交错时，时间线归属可能不是通知原始任务所在的回合。本决策不推断通知与原始请求的因果关系，也不改变旧回答的归属；如需精确关联，应另行持久化源回合关系，而不是用最近时间或 objective 猜测。

验证覆盖两成员委派、提问、双向可见续跑与停止回传的连续服务流程，旧版无标记工作项的读取与阻断，以及真实工作项恢复后仍可通知的边界；均使用受控 Runtime，不访问真实 Provider。
